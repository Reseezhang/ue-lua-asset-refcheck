# 我给 UE 项目写了个"资源点名器"：检查 Lua 引用的资源到底存不存在

> 工具已开源：<https://github.com/Reseezhang/ue-lua-asset-refcheck>。
> 零依赖、只读磁盘、不启动引擎，既能查「写的资源在不在」，
> 也能反查「改这个资源会牵到谁」。

## 起因：一种不会报错的错误

UE 项目里，代码加载资源长这样：

```lua
UE.UObject.Load("/Game/Art/UI/T_LoginBg")
UE.UClass.Load("/Game/Art/UI/WBP_Login.WBP_Login_C")
```

资源路径本质上**只是一串字符**。它写错了、资源改名了、资源被删了——
编译器不管，引擎启动不管。只有真正打开那个界面、触发那段逻辑时，
才会黑屏、空白或者崩。

这带来一个很尴尬的局面：**这类问题在测试之前几乎发现不了，一测才发现，
然后就是来回沟通定位。** 尤其当资源被批量改名或搬迁时，散落在几十个脚本和
配置表里的旧路径，靠人一个个翻是不现实的。

于是我想做个工具。做下来最深的体会是：**这个想法的难点不在"能不能扫到"，
而在"判得准不准"**。下面把我踩过的坑和几次关键判断记一下。

## 第一件事：想清楚它不是扫描器

我一开始的想法很朴素：正则扫一遍 Lua，把 `/Game/...` 抠出来，去磁盘对一遍。

跑是跑通了，命中率大概八成多。但很快发现这个输出**没什么用**，
因为剩下的部分全是噪音：

- Lua 注释里也有资源路径（文档示例、被注释掉的旧代码）——纯误报
- 路径可能是拼出来的：`"/Game/UI/T_Icon_" .. level` ——静态求不出值
- 磁盘上找不到，不代表运行时加载失败（后面细说）

真正有价值的定位是：**它不是"扫描器"，是"资源点名器"**。

打比方：Lua 脚本是一堆点菜单，上面写着"我要这道菜"。工具就是服务员——
把所有菜单上的菜名抄下来，去后厨挨个点名，最后交给你一张
**"点了、但后厨没有的菜"**的清单。

关键在于"服务员"要知道哪些菜名是抄错了、哪些是临时菜、哪些后厨其实有
只是叫法不同。换句话说，**判定语义**才是核心，字符串匹配只是最前面的一小步。

## 关键洞察：三类来源，三种修法，不能混在一起扫

这是我做的第一个重要判断：把"谁引用了资源"拆成三条链路，分别处理。

| 链路 | 来源 | 出问题时要改哪里 |
|---|---|---|
| 脚本引用 | Lua 脚本里直接写的路径 | 改 Lua |
| 源表引用 | 导表工具的 `.xlsx` 源表 | **改表格后重新生成**，改生成的 Lua 无效 |
| 资产引用 | 每个 `.uasset` / `.umap` 内部 | 在编辑器里改资产 |

第二行最容易做错。很多 UE 项目的 Lua 配置表是**导表工具自动生成的产物**，
真正的路径写在 Excel 里。如果只扫 Lua，你会得到"这些路径写错了，去改脚本"
的结论——**而这是完全错误的**，改脚本下次导出就被覆盖了。

我在工具里加了一个配置项来标记这类产物目录，报告里单独把它们标注出来：
"这些引用来自自动生成产物，源头见配置表"。

## 踩坑：我差点被自己的工具骗了

这是整个过程里最值得记的一件事。

处理好上述问题后，我加了一个功能：扫描每个 `.uasset` 的字节，
提取资产之间的引用，构建依赖图。跑完之后报告里出现一个惊人的结论：

> **有 1500 多条引用指向不存在的资源，涉及 700 多个资产。**

看起来工程里埋了颗大雷。但数量级实在太可疑了——一个正常维护的项目
不该有这么大面积的问题。我决定先怀疑工具自己。

回头去看原始字节，答案很快出来了：

```
字符串长度前缀 = 27                  ← 恰好是「完整路径 26 字符 + 结尾符」
对应内容 = "/Game/Game/UI/CommonButton"    ← 完整，合法
我按挂载点切出来的 = "/Game/UI/CommonButton"   ← 这条根本不存在
```

**是我的 bug。** 我写了一个"如果一个匹配里粘连了多条路径，就按挂载点切开"
的处理。而这个工程里恰好有一层目录也叫 `Game`，于是 `/Game/Game/UI/X`
这种完全合法的路径被我砍成了 `/Game/UI/X`，凭空造出上千条假缺失。

删掉那个"聪明"的切分逻辑之后，缺失数从约 1900 降到 **151**。

教训我记到现在：**当工具报出的"系统性大问题"数量级异常时，先怀疑工具自己。**
宁可漏报，也不要把正常路径切坏。这条比工具本身值钱。

## 真正的难点：不是"有没有"，而是"能不能信"

这是全文我最想分享的一点。

假设你这个工具只输出"存在 / 不存在"两个答案。看起来干净利落，
但实测下来**将近四成的结论会是错的**。

我把所有引用边做了可信度分档：

```
HIT     ██████████████████████████████  63%   磁盘上存在，可直接采信
FAMILY  █████████                         18%   同名前缀族，多半有效
META    ████████                          16%   导入元数据噪音，要剔除
STALE   █                                  2%   真的找不到
DIR                                        1%   目录引用，忽略
```

只有第一档能直接用。剩下 37% 不是"错"，而是**需要另行判断**——
而且我把它们全部标注出来了，不需要人去猜。

### 其中最容易误判的一类：FName 的编号被剥离了

这个知识点值得单独说，因为它会直接导致误判"资源被删了"。

UE 的 FName 带编号机制，会把 `T_Cloth_9` 拆成**名字 `T_Cloth` + 编号 9**，
落盘后字符串里只剩下 `T_Cloth`。所以你在一堆贴图里看到引用
`/Game/.../T_Cloth`，**并不代表引用了不存在的资源**：

```
引用里写的：  /Game/.../T_Cloth        ← 磁盘上确实没有这个文件
磁盘上实际：  T_Cloth_0 .. T_Cloth_55  ← 有 56 个
```

这类占实测引用边的一成以上。不做区分，它们会全部被误报成"资源缺失"。
工具的做法是把整族列出来，告诉你"这是同名前缀族，请展开到整个族去看"。

### 另一类：资产内嵌的导入元数据

`.uasset` 里会内嵌一份导入来源记录，形如：

```json
{ "SourceFile": "/Game/Imported/SomeMaterial" }
```

这是**导入时的来源记录，不是运行期依赖**，但它是完全的合法路径字符串。
这类噪音占到了 16%，做影响面分析时必须剔除，否则结论会严重偏大。

## 技术取舍：为什么我不去解析 uasset 的格式

一开始我想找个"正规"方案：解析 UE 的包结构，读它的 Name Table 和
Import Table，拿到精确的依赖关系。

实测之后放弃了。原因是：

**UE5 的 `.uasset` 里，包路径并不集中在 Name Table。** Name Table 主要装
属性名和类名，我实测的那几个文件里甚至一条 `/Game/` 路径都没有；
真正的引用散落在文件的其它位置。

要精确解析就得跟着引擎版本一路跟下去，性价比极低——而且引擎自带的
Asset Registry 导出插件在很多发行版里并不附带。

所以我换了个"笨"办法：**全文件字节扫描 + 上下文分类**。

- 不解析任何 UE 结构，只管捞路径字符串
- 用上下文判断它是真依赖还是导入元数据噪音
- 剩下的不确定性用分类和提示标注出来，交给人工

效果：**约 3500 个资产、数 GB，扫描只要十秒级**，而且能正确捞出真实依赖。
我拿动画蓝图抽检过——它能正确提取出骨骼和物理资产，和编辑器里看到的一致。

代价就是要处理上面说的两类噪音。但我觉得这笔交易很划算：
**80% 的准确率 + 100% 的透明度，比 95% 的黑盒更有用。**

## 从"查错"到"评估影响面"

正向扫描做完之后，我发现它其实只解决了一半问题。

真正高频的场景不是"哪里有错"，而是：**我要改一个资源，会不会出问题？**

比如你要改一个全局字体，或者删一个看着没人用的贴图。这时候你想知道的是
影响面。而这件事**引擎帮不了你**——因为 Lua 是运行时通过字符串加载资源的，
**引擎的依赖图里根本没有"Lua → 资源"这一环**。

补上这一段，恰好就是这个工具的独特价值。所以第二阶段我做了反向查询：

```bash
python refcheck.py query /Game/Art/UI/T_LoginBg
```

它会告诉你四件事：

1. 哪些**业务脚本**直接引用了它（改之前要回归的）
2. 哪些**配置表字段**引用了它（改之前要同步的表格）
3. 哪些**资产**依赖它（受影响的界面 / 关卡 / 材质）
4. 哪些脚本是**间接**受影响的——经资产链传递后的第二跳

第 4 条是关键。举例：你改了一张贴图，看起来只有某个材质用到它；
但这个材质被某个界面用了，这个界面又被某个脚本打开了——那个脚本也得回归。

更妙的是，因为索引里存了"同名前缀族"和"路径少一级"这类提示信息，
查一个资源时，**那些写错了路径但其实指向它的引用，也会被算进来**。
这避免了一个很坑的结论："这个资源有十几处引用啊，怎么工具说 0 处？"
——因为那十几处都写错了目录名。

## 必须说清楚的边界：磁盘缺失 ≠ 运行时失败

这是我最想强调的一条，也是我在每份报告里都加一句警告的原因。

现在很多 UE 项目会启用**打包分包**（`bGenerateChunks`）和**热更下发**。
资源可能压根不在磁盘上，而是躺在 pak 包里或者要运行时下载。

这意味着：**"磁盘上找不到"不等于"游戏里会崩"。**

所以这个工具输出的**永远是"待核查清单"，不是"bug 清单"**。
报告里有一节"环境自检"：如果未命中率异常高（比如超过 25%），
第一件事不是去看清单，而是先确认版本管理是不是没同步完整——
否则清单里会混进大量假阳性。

**先说清楚哪些结论不可信，比多报几条更有价值。** 这句话我在做这个工具的
过程中反复验证过。

## 结果

最后贴一下这个工具现在的样子。它是个纯标准库的 Python 脚本，
零第三方依赖，Python 3.8+ 就能跑，不启动引擎、不联网、只读磁盘。

三个入口：

```bash
python refcheck.py scan    # 正向：脚本里写的资源在不在
python refcheck.py index   # 建索引（反向查询的前置）
python refcheck.py query   # 反向：改它会牵到谁
```

在实测的项目上：

- 扫了 300 多个 Lua 脚本、约 3500 个资产（数 GB），全量索引十秒级
- 构建出约 8000 条资产间引用边
- 分类分布如上：63% 可直接采信、18% 同名前缀族、16% 噪音、2% 真找不到

顺手捞出的真问题包括：一次批量改名搬迁之后引用没跟着改、
配置表里几十条路径指向不存在的资源、以及一个确定的错别字
（资源名多写了一个字母，同一个文件里就有正确写法可以对照）。

## 一些可复用的经验

如果你也在做类似的静态分析工具，这几条可能有用：

1. **先想清楚输出给谁看。** "存在 / 不存在"这种二元结论看着干净，
   但如果不标注可信度，用的人会被误导。
2. **分档不是模糊，是诚实。** 把"我不确定"的 37% 明确标出来，
   比强行给一个 100% 确定的错误答案有用得多。
3. **数量级异常先怀疑工具。** 我自己造出过 1500 条假问题，
   差点当成真 bug 报出去。
4. **区分"文件在不在"和"运行时能不能加载"。** 打包和热更会让这两件事分家。
5. **注意"生成产物"。** 很多工程里的配置是自动生成的，
   改生成物是白改，得找到真正的源头。
6. **给候选，别只给结论。** 未命中时给出"同目录最相近的真实资源"，
   能省掉大量人工翻找——实测大量问题是改名搬迁，而不是资源消失。

